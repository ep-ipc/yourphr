## Methodology

Generated by `scripts/baseline-profile.ts`, ported from ngdpbase's `baseline-profile.sh`. It boots `e2e/server.ts` — the real app over the fixed synthetic household the E2E suite uses — so two releases are measured against the same data. Cold start is the time from spawning it until `/api/health` answers, which includes seeding the household and its first sync. Each route gets 5 discarded warm-up requests, then the MEDIAN of 10 timed ones; a route that answers an error fails the run rather than being timed. Member routes are signed in as the E2E member, admin routes as the instance's generated admin. Memory is the resident size of the server process — the one listening on the port, not the `npx`/tsx wrappers around it — read with `ps` after sampling. Numbers are for comparing releases on one machine, not for sizing a deployment: a real household's database is far larger.

## Why memory rose, measured

The +54 MB is the E2E household, not the product. v3.12.0 seeds more into `e2e/server.ts` for #690 — a 569 KB DICOM and a 176 KB PDF as Binary records, plus an allergy, an immunization, a practitioner and an encounter — and this baseline boots that server.

Measured on this machine, 2026-09-30:

| Build | Seed data | Resident memory (runs) |
| --- | --- | --- |
| v3.11.0 | v3.11.0's | 399.8, 426.5, 467.6 MB |
| v3.12.0 | v3.11.0's | 399.9, 400.1, 404.2 MB |
| v3.12.0 | v3.12.0's | 449.2 – 453.8 MB (one outlier run at 518.4 MB, which first tripped the 25% threshold) |

Same seed data, same memory: the product code adds nothing measurable. From this release on, the comparison is against the larger household.
